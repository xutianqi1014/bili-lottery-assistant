# B站互动抽奖助手使用说明

版本：`0.1.5`

适用程序：`BiliLotteryAssistant.exe` 或源码启动的本地 HTML 控制台
默认地址：<http://127.0.0.1:8787/>

## 1. 软件用途与当前支持范围

软件读取已配置 UP 的 B 站图文/专栏来源，生成动态候选，再依据用户确认的不可变运行计划处理官方、预约和非官方互动抽奖。

当前代码注册三个内置来源。首页和“来源发现”页会显示来源选择器；切换来源后必须重新开始只读发现。

| 来源 | UP MID | 来源页面 | 适配器 | 选择规则 |
|---|---:|---|---|---|
| 你的抽奖工具人 | `100680137` | <https://space.bilibili.com/100680137/upload/opus> | `lottery_toolman_v1` | 分别选择“抽奖合集”和“官方抽奖合集”后缀最大的合集，每类取最新 5 篇；动态类型仅允许官方、非官方 |
| 糯米是个背包 | `492426375` | <https://space.bilibili.com/492426375/upload/opus> | `nuomi_backpack_v1` | 只保留名称为四位年份的合集，选择年份最大的合集，取其中序号最大的 3 篇；动态类型仅允许官方、预约 |
| 番茄薯条喵 | `3546836235193146` | <https://space.bilibili.com/3546836235193146/upload/opus> | `tomato_fries_v1` | 只选择名称为“互动抽奖”的合集，按专栏发布时间取最新 3 篇；跳过上期传送门和充电抽奖，仅处理预约、官方和非官方互动动态 |

“糯米是个背包”来源的当前实际发现证据为：年份合集 `2026`，readlist <https://www.bilibili.com/read/readlist/rl1016769>；最新三篇来源专栏为 `cv52291201`、`cv52318526`、`cv52347493`，其中最新一篇对应动态 <https://www.bilibili.com/opus/1236417468474327060/?from=readlist>。来源结构由 `backend/source_adapters/nuomi_backpack/adapter.py` 单独实现，不会改变默认 UP 的规则。

该 UP 的年份合集同时包含互动抽奖和预约抽奖：互动抽奖使用既有官方互动抽奖流程；页面出现精确的“预约”/“已预约”按钮时识别为新的“预约抽奖”类型，使用预约按钮的点击与终态确认流程。预约参考动态为 <https://t.bilibili.com/1221942213171216387?spm_id_from=333.1369.0.0>。其他 UP 的来源结构不能直接套用这两个适配器，必须增加独立来源配置和适配器。

“番茄薯条喵”来源的上传页通过 `GET https://api.bilibili.com/x/article/up/lists?mid=3546836235193146&sort=0` 读取合集，只接受名称精确归一化为“互动抽奖”的合集，不会把“转盘合集”当作来源。当前接口实测该合集为 `rl954367`；再通过 `GET https://api.bilibili.com/x/article/list/web/articles?id=954367` 读取成员，按 `publish_time`（缺失时再按文章 ID 和接口位置）倒序取最新 3 篇。参考专栏为 <https://www.bilibili.com/opus/1239314926435041298/?from=readlist>。

该混合合集正文可能先出现“上期传送门”，随后分为充电抽奖、预约抽奖和互动抽奖。解析器会排除带“上期/上一期传送门”的动态链接，并在可见分区状态为 `charge` 时跳过充电动态；只有 `reservation` 和 `interactive` 分区进入动态去重候选。互动分区内的官方/非官方区别仍由执行时动态页面事实分类，预约沿用独立预约流程。未能识别分区时采用包含式白名单并跳过，避免把充电动态误送入写操作。

### 2.2 启动

双击：

`BiliLotteryAssistant\BiliLotteryAssistant.exe`

程序会：

1. 检查 `127.0.0.1:8787` 是否已是本软件服务；
2. 如果已经运行，只打开已有控制台，不启动第二个服务；
3. 如果端口空闲，启动本地 FastAPI 服务；
4. 服务监听成功后自动打开 `http://127.0.0.1:8787/`。

如果 8787 已被其他程序占用，程序会报端口占用错误，不会强制结束其他程序。请关闭占用程序后再启动。

### 2.3 关闭和释放端口

关闭所有打开的本软件控制台页面后，程序等待约 3 秒确认没有页面重新连接，然后停止任务、关闭浏览器和数据库并释放 8787 端口。

刷新控制台页面不会立即停止程序：页面会在约 3 秒宽限期内重新连接。若同时打开多个本软件页面，必须全部关闭才会触发退出。

## 3. 源码启动

要求 Python 3.12 或更高版本：

建议首次使用前在 PowerShell 终端完整运行一次下面的初始化命令。它会重新创建项目虚拟环境、安装开发依赖、安装 Playwright Chromium，并让本次启动使用该 Chromium；以后再次启动时可直接激活 `.venv` 后运行最后两行。

```powershell
deactivate
Set-Location C:\Users\35267\Desktop\b站抽奖\bili-lottery-assistant

py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1

python -m pip install -e ".[dev]"
python -m playwright install chromium

$env:BILI_BROWSER_CHANNEL='chromium'
python -m backend.launcher
```

然后打开：<http://127.0.0.1:8787/>

其中 `$env:BILI_BROWSER_CHANNEL='chromium'` 只对当前终端窗口有效。若不设置该变量，源码默认使用 Microsoft Edge（`msedge`），需要系统已安装 Edge。浏览器登录资料保存在本机应用数据目录，不会提交到 GitHub。

## 4. 首次登录和登录页规则

1. 打开控制台首页“概览与准备”。
2. 点击“打开登录页”。
3. 在自动打开的 B 站浏览器页面完成登录、扫码或验证。
4. 登录完成后返回控制台，点击“开始只读发现”。

登录页具有唯一性：

- 登录页已经打开时，再次点击只会把已有页面切换到前台，不会重复新建页面；
- 关闭登录页后再次点击，会重新创建登录页；
- 自动化浏览器被关闭后再次点击，会重新创建浏览器会话；
- 不要在执行期间手动关闭或操作自动化使用的 B 站页面。

## 5. 首页运行配置

首页的“DeepSeek 与提及好友配置”表单对应 `/api/settings` 接口。

### 5.1 DeepSeek 字段

| 字段 | 作用 |
|---|---|
| DeepSeek API Key | 生成非官方动态评论；输入框为密码框，接口只返回是否已配置 |
| API 地址 | 默认 `https://api.deepseek.com/chat/completions` |
| 模型 | 默认 `deepseek-v4-flash` |
| 固定 @账号 1–3 | 动态要求 @好友时按顺序补充，最多 3 个 |

点击“保存设置”后，Key 只保存在当前 Python 进程的设置对象中，不写入数据库、运行计划或日志；关闭程序后需要重新输入。

### 5.2 安全要求

- 不要把 Key 写进代码、截图、问题网址或 GitHub Issue；
- API 地址必须是带主机名的 `http` 或 `https` 地址，不能携带用户名和密码；
- 动态要求的 @好友超过 3 个时，程序在任何 B 站写操作前阻塞该条；
- 未配置 DeepSeek 时，非官方条目不会在评论写入前继续执行。

## 6. 四页界面和按钮

### 6.1 概览与准备

显示本地服务健康状态、浏览器会话状态、当前来源和运行配置。主要按钮：

- “选择来源”：在已启用的 UP 配置之间切换；切换后清除当前发现和运行计划，必须重新发现；
- “打开登录页”：调用 `POST /api/account/open-login`；
- “保存设置”：调用 `POST /api/settings`；
- “打开 B 站主页”：打开当前来源配置的 UP 专栏页。

### 6.2 来源发现

主要按钮：

- “开始只读发现”：调用 `POST /api/source-profiles/{profile_id}/discoveries`；
- “刷新”：调用 `GET /api/discoveries/{discovery_id}` 和问题列表接口。

发现卡片显示：

- 已检查专栏数；
- 未知标记数；
- 动态 ID 全局去重后的数量；
- 自动计划状态；
- 两类来源专栏的点赞判定、解析状态和决策；
- 动态候选与它们的来源关系。

只读发现阶段不打开候选动态，不读取评论列表，也不执行候选动态的评论、转发、点赞或关注。

### 6.3 执行与结果

如果发现后没有待处理动态，页面显示“没有待处理动态，本轮不生成执行计划”。

如果存在待处理动态，计划会由后台自动生成，页面显示：

- “确认并开始执行”：依次调用 `POST /api/runs/{run_id}/confirm` 和 `POST /api/runs/{run_id}/start`；
- 页面刷新后若计划已经处于 `confirmed_waiting_user`，保留“开始执行计划”作为恢复入口，调用 `POST /api/runs/{run_id}/start`；
- “继续下一条／重新检查当前条目”：仅在运行暂停且允许恢复时出现，调用 `POST /api/runs/{run_id}/resume`。
- “重新开始”：仅在当前运行处于 `waiting_user` 或 `interrupted` 且存在人工复核阻塞时出现。请先在 B 站手动完成或修正当前错误动态，再点击该按钮；它调用 `POST /api/runs/{run_id}/restart`，只将当前未完成动态重置为重新检查，已完成和已跳过动态不会重复执行。
- “跳转到当前动态”：优先定位 `running`、`waiting_user` 或阻塞状态的当前条目；动态处理间隔中则定位第一个未处理条目；全部动态完成后定位最后一个已完成或已跳过条目。按钮会平滑滚动到对应动态并高亮该行；这是页面内定位操作，不会打开新网页，也不会调用 B 站写接口。计划为空时按钮禁用。

确认后计划的动态范围、顺序和来源关系不可修改。运行表格只展示序号、动态、流程、页面状态、运行状态。

### 6.4 运行日志（第四页）

“运行日志”页复用 `/api/events` 实时事件流，不生成与后端状态无关的统计数据。日志保存在当前页面会话的内存中，切换前三页不会丢失。

- 正常事件（例如 `run.started`、`run.item_started`、`run.item_updated`、`run.finished`）只显示时间、级别和一句中文摘要，避免连续处理大量动态时刷屏。
- `waiting_user`、`failed`、`interrupted`、`cancelled`、阻塞事件和新记录的问题网址显示详细上下文，包括问题网址、页面阶段、错误码、安全详情和事件数据；字段名包含 Key、Token、Cookie、Secret、Password 或 Authorization 的值会显示为 `[REDACTED]`。
- “复制日志”优先使用浏览器剪贴板 API，不支持时使用本地文本框回退；“清空”会先要求确认，确认后只清除当前页面会话日志，不改变数据库中的运行记录或问题记录。
- 日志页只读展示，不会触发 B 站页面打开、点赞、评论、转发、关注或官方参与动作。

## 7. 发现规则

发现入口和通用去重流程相同，但合集选择由每个来源适配器单独决定：

1. 读取所选 UP 的图文/专栏上传页对应的 B 站文章列表接口；
2. `lottery_toolman_v1` 对默认 UP 找到“抽奖合集”和“官方抽奖合集”，按后缀数字分别选最大合集，每类取最新 5 篇；
3. `nuomi_backpack_v1` 只接受名称为四位年份的合集，按年份选择最大者，再按原始序号取最大 3 篇；
4. 检查选中来源专栏是否已点赞；
5. 解析来源专栏引用的动态；
6. 按动态 ID 全局去重，但保留一个动态对应的全部来源关系；
7. 已点赞来源专栏标记为已处理，不作为本轮来源点赞目标；
8. 未点赞且解析成功的来源专栏及其动态进入候选范围。

预约抽奖不在只读发现阶段打开动态判断。候选动态统一在正式执行当前条目时读取页面。读取页面正文和标题、确认不是 B 站错误页后，第一优先级是读取动态右侧点赞标记；若已点赞，立即按已参与跳过，不再收集官方入口、预约卡片或非官方结构证据，也不执行类型分类和来源类型白名单判断。只有未点赞时，才继续判断动态类型：若存在官方互动抽奖入口，按官方互动抽奖处理；否则只有页面正文出现精确的“预约有奖”卡片文案，或预约卡片按钮精确显示“已撤销”时，才分类为独立的 `reservation`；“预约”“已预约”按钮用于读取可执行状态，而按钮变成“已结束”“预约已过期”“去观看”或“已撤销”只表示预约卡片不可执行的终态；其中“已撤销”专门兼容 B 站撤销直播后移除“预约有奖”文案的页面，不单独把普通动态分类成预约。仍无官方入口或上述预约卡片信号时才按非官方规则处理。这样不会用来源合集标签替代动态页面事实。运行时还会应用来源配置中的 `activityTypes` 白名单：默认来源只接受 `official`/`unofficial`，糯米来源只接受 `official`/`reservation`。预约不会因为页面同时出现评论/转发/关注文字而改判成非官方；当未点赞页面类型不在当前来源白名单内时，条目进入 `SOURCE_ACTIVITY_TYPE_NOT_ALLOWED` 人工复核状态，不执行任何外部写操作。

如果动态已经被删除、下架或不可见，B 站可能只显示标题“出错啦! - bilibili.com”以及“返回上一页/换一张”，也可能显示“动态不存在”“内容已被删除”等明确文案。运行时在读取点赞、抽奖入口和预约卡片前识别这些错误页，返回 `DYNAMIC_UNAVAILABLE_SKIPPED`，将条目标记为 `skipped` 并继续下一条；不会把错误页误判为非官方，也不会因为来源白名单而产生 `SOURCE_ACTIVITY_TYPE_NOT_ALLOWED`，同时不执行任何写操作。

## 8. 官方抽奖执行流程

官方自动化默认开启，配置项为 `BILI_OFFICIAL_AUTOMATION_ENABLED=true`。

每条官方动态按以下顺序执行：

1. 打开 `https://www.bilibili.com/opus/<数字ID>`；
2. 在任何类型证据和互动抽奖入口读取之前，读取动态右侧点赞状态；
3. 若已经点赞，返回 `ALREADY_PARTICIPATED_LIKED`，将条目标记为跳过，不判断动态类型、不打开抽奖面板；
4. 仅当未点赞时，才要求页面存在唯一官方互动抽奖入口 `a[data-type="lottery"]`；
5. 打开互动抽奖入口，等待官方抽奖 iframe 加载；
6. 读取面板文本，面板文本最多轮询约 10 次、每次间隔 500 毫秒；
7. 如果面板先显示“已成功参与”“已参与”“已转发”等终态，返回 `ALREADY_PARTICIPATED`，不点击参与按钮；
8. 如果面板没有“开奖时间”字段，按 `LOTTERY_EXPIRED` 处理并跳过；
9. 如果存在开奖时间，读取参与按钮；只有唯一且文本在允许列表内的按钮才会点击；
10. 点击后最多轮询约 30 次、每次间隔 500 毫秒，等待成功或明确失败终态；
11. 成功后先关闭互动抽奖面板，并确认 iframe 和关闭控件均消失；
12. 面板关闭后点击动态点赞并确认点赞标记点亮；
13. 得到明确终态后，等待下一条官方动态的随机间隔，默认 3–5 秒。

官方参与按钮文本允许列表包括“关注UP主并转发抽奖动态”“关注我并转发抽奖动态”“转发抽奖动态”等有限文本。按钮不唯一、面板读取失败、验证码/风控或点击后终态未知时，当前条目停止，记录问题网址，不自动重试。

## 9. 预约抽奖执行流程

预约抽奖是独立的运行时类型 `reservation`，但因为它和互动抽奖共用已确认官方执行范围，所以在运行计划中进入“官方”执行队列，不会误走非官方评论/转发流程。

每条预约动态按以下顺序执行：

1. 打开当前动态的规范 `https://www.bilibili.com/opus/<数字ID>` 地址，并在任何预约或其他类型证据读取前读取动态点赞标记；
2. 若动态点赞已激活，返回 `ALREADY_PARTICIPATED_LIKED`，直接跳过，不判断动态类型、不点击预约、不检查关注；
3. 仅当未点赞时，才确认页面正文存在“预约有奖”卡片，或确认预约卡片（`.bili-dyn-card-reserve__card`）内的可见按钮精确显示“已撤销”，再读取该预约卡片内的可见按钮；只接受精确文本为“预约”或“已预约”的可执行控件。“已结束”“预约已过期”“去观看”和“已撤销”只作为已识别预约卡片的不可执行终态读取，不点击预约、点赞或关注。若点击“预约”后页面短暂在 `[role="alert"]` 节点显示“预约已过期”，立即返回 `RESERVATION_EXPIRED` 并跳过，不等待到未知终态；卡片外的同名按钮不会被使用；
4. 只有一个“已预约”且没有“预约”时，视为预约状态已存在，不重复点击；若恰好一个可用“预约”按钮，则只点击一次；
5. 点击后轮询按钮和页面正文，直到看到“已预约”或“预约成功/已参与抽奖”；
6. 预约状态确认后，点击动态点赞并要求点赞标记激活；点赞是预约抽奖跨运行的参与标记；
7. 打开动态作者主页检查关注状态；若显示“关注”，点击一次并轮询至“已关注/互相关注”；已经关注则不重复点击；
8. 预约、动态点赞和作者关注均确认后返回 `RESERVATION_CONFIRMED`。控件重复、禁用、点击异常、关注控件不唯一或任一终态无法确认时停止当前条目并记录问题网址，不自动重试。

预约流程不会打开互动抽奖 iframe，也不会点击评论或转发。动态中没有开奖时间字段的预约卡片不会被强行当作互动抽奖过期处理。关注检查和补关注使用作者主页的唯一可见 `.space-follow-btn`，不会从搜索结果中的其他账号猜测作者。

## 10. 非官方抽奖执行流程

非官方自动化默认开启，配置项为 `BILI_UNOFFICIAL_AUTOMATION_ENABLED=true`。

### 9.1 运行时分类

- 页面存在唯一官方互动抽奖入口时，判定为官方；
- 加码/转发动态如果包含 `.bili-dyn-content__orig.reference` 原动态层，官方入口只在当前外层动态范围内计数；嵌套原动态中的官方入口仅作为被引用内容，不会把外层动态改判为官方，也不会交给官方自动执行器；
- 只要没有稳定官方入口，就按非官方处理；
- 非官方再根据转发叠层是否存在原动态细分为普通或加码；
- 普通和加码的实际动作策略相同，均使用评论框的“同时转发到我的动态”复选框。

因此，加码动态 `https://t.bilibili.com/1238160555189993490` 即使在嵌套原动态中显示互动抽奖，也应按外层非官方加码流程执行：评论并勾选同步转发、点赞、关注；不会因为内层官方入口触发 `OFFICIAL_AUTOMATION_TARGET_OUTSIDE_CONFIRMED_RUN`。

### 9.2 动作顺序和等待

每条非官方动态执行：

1. 打开动态后随机等待 1–2 秒，再进行首次页面读取；
2. 在收集非官方正文、转发和作者结构之前检查当前动态右侧点赞状态；已点赞返回 `ALREADY_LIKED_SKIPPED`，整条跳过且不判断动态类型；
3. 仅未点赞时读取当前动态自身正文，不使用评论列表生成要求；
4. 调用 DeepSeek 生成简短评论；
5. 追加动态正文中要求且评论尚未包含的话题标签；
6. 按动态要求从设置表单的固定账号中补充最多 3 个 @好友；
7. 填写评论，勾选“同时转发到我的动态”，点击唯一可见的发布按钮；
8. 评论发布按钮点击完成且没有异常即返回 `COMMENT_SUBMIT_ACCEPTED`，不等待评论列表立即显示；
9. 复核评论同步转发的终态；
10. 随机等待 1–2 秒，点击动态点赞并确认点亮；
11. 随机等待 1–2 秒，打开作者主页并检查关注状态；
12. 通过动态作者的 `space.bilibili.com/<mid>` 链接优先直达作者主页；没有可用链接时，打开作者搜索页，随机等待 1–2 秒，再匹配唯一精确作者；
13. 得到评论、转发、点赞和关注的明确终态后完成本条。

关注按钮、点赞按钮、同步转发控件或作者主页不唯一时，当前条目阻塞并记录问题网址。任何已经发生写入但终态未知的动作都不会自动重试。

## 11. 来源专栏收尾

所有动态进入安全终态后，程序重新计算来源专栏收尾：

- 初始已点赞：显示“已点赞”，不重复点击；
- 初始未点赞、关联动态全部终态且没有开放问题：等待 3–5 秒后自动给来源专栏点赞，并复核点亮；
- 关联动态未全部终态或存在问题网址：显示“阻塞”，本轮不点赞；
- 来源点赞终态未知或失败：记录来源专栏网址，停止收尾，不自动重试。

当前配置 `BILI_SOURCE_LIKE_AUTOMATION_MAX_ITEMS_PER_RUN` 默认值为 `10`，表示一次运行最多自动收尾 10 个来源专栏；可通过环境变量调整。

## 12. 结果状态如何理解

| 状态/代码 | 含义 |
|---|---|
| `completed` | 当前条目动作已获得明确成功终态 |
| `skipped` | 已点赞、已参与、抽奖已结束或动态页面已消失，未重复写入 |
| `waiting_user` | 页面结构、控件或写入终态需要人工复核 |
| `blocked_unknown` | 点击或读取后的外部结果未知，禁止自动重试 |
| `blocked_failed` | 安全检查或控件检查失败，未允许继续写入 |
| `ALREADY_PARTICIPATED_LIKED` | 动态已经点赞，按已参与跳过 |
| `ALREADY_PARTICIPATED` | 官方互动抽奖面板明确显示已参与，未点击按钮 |
| `LOTTERY_EXPIRED` | 官方互动抽奖面板没有开奖时间字段，按已结束处理 |
| `RESERVATION_EXPIRED` | 预约卡片已结束、已过期、已撤销，或点击后显示“预约已过期”，安全跳过 |
| `RESERVATION_WATCH_ONLY_SKIPPED` | 预约卡片显示“去观看”，当前不可预约，安全跳过 |
| `DYNAMIC_UNAVAILABLE_SKIPPED` | B 站显示动态错误页或明确不可见文案，安全跳过 |
| `ALREADY_RESERVED` | 旧版本兼容结果：预约控件已显示“已预约”，未重复点击 |
| `RESERVATION_CONFIRMED` | 预约状态、动态点赞和作者关注均已确认 |
| `FOLLOW_ALREADY_DONE` | 作者主页已经显示“已关注/互相关注”，未重复点击 |
| `FOLLOW_CONFIRMED` | 作者主页关注按钮点击后已确认“已关注/互相关注” |
| `COMMENT_SUBMIT_ACCEPTED` | 评论发布按钮已点击且未抛出异常，不依赖评论列表即时显示 |
| `UNOFFICIAL_PARTICIPATION_CONFIRMED` | 非官方评论、转发、点赞、关注均已确认 |

页面底部的问题网址列表是本轮安全记录。对应动态或来源专栏在问题未解决前不会自动补点赞。

## 13. 等待时间总览

| 场景 | 默认等待 |
|---|---:|
| 打开非官方动态后首次读取 | 随机 1–2 秒 |
| 非官方评论/转发/点赞/关注之间 | 随机 1–2 秒 |
| 非官方作者搜索页打开后匹配 | 随机 1–2 秒 |
| 官方动态之间 | 随机 3–5 秒 |
| 来源专栏收尾之间 | 随机 3–5 秒 |
| 官方面板文本水合 | 最多约 5 秒（10 × 500ms） |
| 官方参与后终态轮询 | 最多约 15 秒（30 × 500ms） |
| 预约按钮终态轮询 | 最多约 15 秒（30 × 500ms） |
| 关闭最后一个控制台页面后释放服务 | 约 3 秒宽限期 |

等待时间是防止页面异步水合和避免连续快速操作的运行策略，不代表 B 站一定会在该时间内完成网络响应；终态不明确时程序会停止。

$env:BILI_PORT = "8787"

DeepSeek Key 通过网页设置表单输入，不建议使用环境变量保存；如果必须使用环境变量，变量名为 `BILI_DEEPSEEK_API_KEY`，并应避免把终端历史和日志分享出去。

## 15. 常见问题

### 页面提示端口 8787 被占用

确认是否已有助手实例运行。若已有实例，直接访问 <http://127.0.0.1:8787/>；若不是本软件占用，关闭占用程序后再启动。助手不会强制结束其他程序。

### 点击“打开登录页”没有重复打开页面

这是预期行为：已有登录页时按钮只会把它切换到前台。关闭登录页后再次点击才会创建新页。

### 发现完成但没有执行计划

只有存在待处理动态时才自动生成计划。若所有来源已点赞、动态已参与或没有可解析候选，页面会明确显示不生成空计划。

### 官方条目提示 `LOTTERY_EXPIRED`

当前规则是：互动抽奖面板没有“开奖时间”字段就按已结束处理。该条会跳过，不点击参与按钮。

### 非官方条目提示 `COMMENT_*`、`FOLLOW_*`、`*_NOT_UNIQUE`

表示评论、同步转发、点赞、关注或作者匹配没有唯一且可确认的控件。程序会停止当前条目并保留问题网址，不能通过重复点击强行继续。

### 评论已经发出但界面看不到

当前版本不再复检评论列表。B 站评论可能延迟渲染；只要唯一发布按钮点击没有异常，就记录 `COMMENT_SUBMIT_ACCEPTED`。转发、点赞和关注仍需终态确认。

### 互动分段为什么仍可能变成官方或非官方

番茄薯条喵的参考专栏 `1239314926435041298` 在正文中把动态分成“预约抽奖”“互动抽奖”和“充电抽奖”。解析阶段会把每个动态的分段写入来源起源和执行计划：预约显示“预约”，互动显示“互动”，充电被排除。互动分段不是 B 站页面类型，它同时允许官方互动抽奖和普通/加码非官方抽奖；打开动态后仍以页面实际 DOM 信号做最终分类。这样可以避免把来源合集的 `official` family 误当成每条动态都必然是官方抽奖。

动态打开后的第一项读取固定为点赞状态：

1. 先查找外层动态唯一可见点赞控件及 active/`aria-pressed`/`data-state` 等状态标记；
2. 已点赞返回 `ALREADY_PARTICIPATED_LIKED`，跳过后续类型判断、互动抽奖面板、预约卡片、评论、转发和关注；
3. 明确唯一且未激活才继续官方/预约/非官方分类；
4. 找不到点赞控件或可见控件不唯一时返回 `ACTIVITY_LIKE_STATE_UNKNOWN`，在类型判断前暂停，当前条目不执行任何写操作。

因此，已有点赞不会再被非官方流程误认为“未参与”而先评论/转发后取消点赞。运行计划中的“互动”只是来源分段标签；运行时检查完成后，条目会更新为实际的“官方”“预约”或“非官方”。

界面中的分类展示统一使用“互动”替代原来的“官方”标签。这里仅改变用户界面的分类名称；程序内部仍保留 `official` 运行模式，用于选择 B 站互动抽奖面板流程和对应的安全检查。因而“互动”标签下仍可能执行官方互动抽奖流程，也可能在打开后按页面信号进入非官方流程。

### 程序停止后是否可以直接继续

只有运行状态为允许恢复且没有外部写入未知结果时，页面才显示“继续下一条／重新检查当前条目”。如果上一次在点击后终态未知，必须先人工检查并完成 B 站页面上的当前动态，再点击“重新开始”；该按钮只重新检查当前未完成动态，不会重复执行已完成或已跳过条目。

## 15. 安全和使用注意事项

- 本软件会在已登录的 B 站账号下执行真实评论、转发、点赞、关注和官方抽奖参与动作；点击“确认并开始执行”（刷新后已确认计划显示“开始执行计划”）即表示允许这些写操作。
- 执行期间不要手动操作自动化浏览器页面、关闭弹窗或切换目标动态。
- 遇到验证码、风控、登录失效、页面结构变更或控件不唯一时，应停止并人工复核；动态正文中普通的“登录”字样不会单独触发安全阻断，只有实际验证/风控提示仍会阻断。
- 不要分享包含 Cookie、浏览器会话、DeepSeek Key、数据库或日志的目录。
- `BiliLotteryAssistant.exe` 必须与 `_internal` 目录一起使用。
